**Target:** `src/searching`
**Status:** Phases 0 and 1 complete — the `vector` provider works end to end. Phase 2 next.

*"how do I reset my password"* finds a document titled *"Credential recovery procedure"*.

## 1. Where the service stands today

Everything below is grounded in the current code, not assumed. The service is in better shape for
this than most — the extension points already exist.

- **One local engine.** `src/searching/providers/searching.js` (1,660 lines) is a field-aware
  inverted index: per-field tokenisation, BM25 scoring with tunable `k1`/`b`, prefix and fuzzy
  expansion, synonyms, quoted-phrase gating, compositional `autoSuggest`, and match-centred
  snippets. `tokens`, `memory` and `files` are aliases for it.
- **Multiple named indexes.** A `containers` `Map` holds `{ tokens, documents, fieldStats }` per
  index name. Every public method already routes through `getContainer_()`, so a fourth
  per-container structure slots in cleanly.
- **Disk persistence.** `_saveContainerToDisk` / `_loadContainerFromDisk` write `documents.json`,
  `tokens.json` and `meta.json` per container, gated on `DISK_FORMAT_VERSION` (`'2.1.0'`) and a TTL.
  A version mismatch is already handled as "rebuild", which gives us a safe upgrade path.
- **A provider-neutral contract.** `indexerCompat.js` normalises `indexDocument` / `removeDocument`
  / `loadFromDisk` / `saveToDisk` across the local, `api` and `solr` providers, so crawlers can swap
  backends by changing only the factory type. Any new method has to be considered against this
  contract.
- **An options-object search path.** `search(query, containerOrOptions)` already merges instance
  defaults with per-call options via `mergeSearchOptions_` — that is exactly where a `mode` option
  belongs, no signature change required.
- **Routes, UI and a client library.** `routes/index.js` (570 lines) exposes ~18 REST endpoints
  including a `POST /api/search/:searchContainer` that already forwards an arbitrary options body.
  `views/index.html` has Dashboard / UI / Data / Settings tabs; the Settings tab renders itself from
  whatever `getSettings()` returns.

### What is missing

There is no embedding capability anywhere in the repo. `src/aiservice` has six providers (Claude,
OpenAI, OpenAI-KV, Ollama, Gemini, TensorFlow) but the base class `aibase.js` defines only
`prompt()` — no `embed()`. Nothing stores or compares vectors. The `openai` SDK *is* already a
dependency, which removes the main install hurdle.

## 2. The shape of the change

**Decision: a standalone `vectorsearching.js` provider, sibling to `searching.js`.**

An earlier draft of this plan argued for making semantic retrieval an optional mode of the existing
token engine, to avoid duplicating containers, persistence and index management. That was overruled
in favour of a clean separation, and the separation is now the design:

- The two engines are chosen at construction — `type: 'default'` vs `type: 'vector'` — and **share
  no code path**. `providers/searching.js` is not modified at all.
- The semantic engine can change its scoring, persistence and tuning freely, with **zero regression
  risk to BM25** and to the callers depending on it.
- The cost is a duplicated lexical index inside the vector provider. That duplication is deliberate
  and exists solely to serve *its own* `hybrid` and `keyword` modes, so it can diverge from the
  token engine without anyone having to reconcile them.

The vector provider is self-contained rather than semantic-only, so `hybrid` — the mode that
actually earns its keep — works without reaching across to the other engine.

| File | Change | Responsibility |
|---|---|---|
| `providers/vectorsearching.js` | **New** | The whole semantic engine: containers, its own BM25 index, embedding queue, three search modes, persistence, stats, suggestions. |
| `modules/embeddings.js` | **New** | Backend-agnostic embedding client: `embed()`, `embedBatch()`, `chunkText()`, L2 normalisation, cache lookup, retry/backoff. |
| `modules/vectorStore.js` | **New** | Per-container vector index: packed `Float32Array` matrix, docId↔row map, free-list, `knn()`, serialise/deserialise. |
| `modules/fusion.js` | **New** | Combines a BM25 result list and a vector result list into one ranking (RRF and weighted-normalised). |
| `index.js` (factory) | Edit | Register `vector` / `vectorsearching` / `semantic` types. **The only edit to an existing file.** |
| `providers/searching.js` | **Untouched** | Deliberately. The token engine is not in scope. |
| `../aiservice/provider/*.js` | Edit | `embed()` on the base class and on OpenAI / Ollama / Gemini; explicit unsupported error on Claude. |
| `routes/index.js` | Edit | Mode option, semantic status, re-embed backfill, more-like-this. |
| `views/index.html` + `scripts/js/index.js` | Edit | Mode control, weight slider, semantic panel on the dashboard. |

The three `modules/` files stay **shared infrastructure**, not duplicated — they were never part of
`searching.js`, and a future embedding-aware feature elsewhere should reuse them.

> **Backward compatibility is free under this design.** Nothing about the token engine changes, so
> the existing tests in `tests/unit/searching/` are an unmodified regression guard rather than a
> constraint to engineer around.

## 3. The two paths through the engine

Write and read each fork into a lexical branch that exists today and a vector branch that is new.
Nothing on the lexical side moves.

```
WRITE  ·  add() / addAll() / indexDocument() / replace()

                  ┌─ tokenize (per field) ──→ inverted index      [EXISTS]
   document ──────┤                            container.tokens
                  │
                  └─ retain text ─→ chunk ─→ embed queue ─→ vector store   [NEW]
                     doc.text       window    batched,        container.vectors
                                              async


READ  ·  search(query, { mode })

                  ┌─ BM25 (top K) ─────────────┐                  [EXISTS]
   query ─────────┤                            ├─→ fuse ─→ phrase gate ─→ results
                  │                            │    RRF     + filter      maxResults
                  └─ embed query ─→ cosine knn ┘                  [NEW]
                     (cached)        (top K)
```

Two properties of this arrangement matter:

1. **The fusion step is the only place scores mix**, so BM25 tuning and embedding-model choice stay
   independent.
2. **The phrase gate and `filter` run after fusion**, which means a quoted phrase still hard-filters
   results even when a document arrived via the vector branch — a semantically similar document that
   does not contain `"MySQL Enterprise"` is still correctly rejected.

## 4. Decisions to settle before coding

Five choices materially change the work. Each has a recommendation; none needs to block the start of
Phase 0, which is deliberately independent of all of them.

### A · Where do embeddings come from?

Four realistic backends, and they are not mutually exclusive — the embedding client should support
all of them behind one interface:

- **aiservice (OpenAI)** — `text-embedding-3-small`, 1536 dims, supports a `dimensions` parameter to
  truncate to 256/512 without retraining. Best quality-per-effort; the `openai` SDK is already
  installed.
- **aiservice (Ollama)** — `POST /api/embed` with `nomic-embed-text` (768) or `all-minilm` (384).
  Local, free, no egress. Ideal for development and for air-gapped deployments.
- **aiservice (Gemini)** — `text-embedding-004`, 768 dims.
- **Hashing embedder** — no network at all: hash each token into *d* buckets with signed counts,
  then L2-normalise. Quality is poor as semantics but it is deterministic, instant, and free, which
  makes it the right default for tests and for a first-run demo with no keys configured.

> **Recommendation.** Build the client with a pluggable `backend` and ship `hash` plus `aiservice`.
> Default to `hash` when no AI service is wired in, so the feature never hard-fails on a missing key.
> **Note that Anthropic has no embeddings endpoint** — the `claude` AI provider must throw a clear
> "use openai / ollama / gemini, or a Voyage backend" error rather than silently degrading.

### B · How does the searching service reach the AI service?

The obvious move — adding `aiservice` to `serviceDependencies` for `searching` in the root
`index.js` — inverts the layering. `searching` is Level 3; `aiservice` is Level 4 and itself depends
on `workflow`, `queueing` and `caching`. There is no literal cycle today, but it breaks the level
model the registry documents and makes `validateDependencies()` misleading.

> **Recommendation.** Do *not* register a hard dependency. Accept an **optional injected embedder** —
> either `dependencies.aiservice` or a plain `options.semantic.embed` function — the same way
> `caching` is treated as optional today. The composing app (`app.js`) wires the two together
> explicitly. This keeps the dependency graph honest and makes the engine trivially testable with a
> stub function.

### C · Does `add()` wait for the embedding?

Today `add()` is in-memory and returns in microseconds. An embedding API call is 50–500 ms of
network. Making `add()` await it would change the latency profile of every existing caller, and
`addAll()` over 10,000 documents would become an hour of serial round-trips.

> **Recommendation.** Index lexically **synchronously** as now, and enqueue the embedding job. A
> background worker drains the queue in batches (OpenAI accepts up to 2,048 inputs per request).
> Documents become keyword-searchable immediately and semantically searchable moments later. Expose
> `await search.flushEmbeddings(container)` for tests, for bulk-import scripts and for the re-embed
> endpoint, so determinism is available when it is needed.

### D · How are the two rankings combined?

BM25 scores are unbounded and corpus-dependent; cosine similarity sits in [-1, 1]. Adding them
directly, or min-max normalising them per query, produces rankings that swing wildly as the corpus
grows. **Reciprocal Rank Fusion** sidesteps this by using only rank position:
`score(d) = Σ 1 / (k + rank_i(d))`, conventionally with `k = 60`.

> **Recommendation.** RRF as the default for `mode: 'hybrid'`. Also implement weighted-normalised
> fusion (`alpha · norm(bm25) + (1 - alpha) · cosine`) behind an `alpha` option, because it is what
> people reach for when tuning by hand and it makes the UI slider meaningful. Both live in
> `modules/fusion.js` and are trivially unit-testable on synthetic rank lists.

### E · How many dimensions, and what does that cost in RAM?

Vectors are held in memory per container. The arithmetic is unforgiving and worth settling before
the default is chosen — `docs × dims × 4 bytes`:

| Documents | 384 dims | 768 dims | 1536 dims | Brute-force query |
|---|---:|---:|---:|---:|
| 1,000 | 1.5 MB | 3.1 MB | 6.1 MB | < 1 ms |
| 10,000 | 15 MB | 31 MB | 61 MB | ~3–10 ms |
| 100,000 | 154 MB | 307 MB | 614 MB | ~40–150 ms |
| 1,000,000 | 1.5 GB | 3.1 GB | 6.1 GB | ~0.5–2 s |

Query timings are **estimates** for a single-threaded dot product over pre-normalised
`Float32Array`s; measure before quoting them.

> **Recommendation.** Default to **384 dimensions**, pre-normalised at write time so query-time
> cosine is a plain dot product. Brute force is genuinely fine up to roughly 100k documents per
> container, which covers the realistic use of this service — so ship brute force and do not build an
> ANN index. Above that, the cheapest escape is not ANN either: take the BM25 top 500 and rerank only
> those by cosine. Add a documented ceiling (`maxVectorDocuments`) that logs a warning when crossed.

## 5. Work breakdown

Six phases, ordered so each one is independently shippable and testable. Phases 0 and 1 deliver a
working feature end-to-end with the hashing embedder; everything after that is quality and reach.

### Phase 0 — Standalone modules, no engine changes  *(~1 day)*

**New · `modules/embeddings.js`**

- `class EmbeddingClient` taking `{ backend, model, dimensions, aiservice, embed, cache, batchSize, maxRetries }`.
- `async embed(text)` and `async embedBatch(texts)`, both returning L2-normalised `Float32Array`s of
  fixed length.
- `hashEmbed(text, dims)` — deterministic, offline, signed-bucket hashing. No dependencies.
- `chunkText(text, { maxChars, overlap })` — sliding window, splitting on sentence boundaries where
  possible. Emits ids matching the `#chunk-` convention `indexerCompat.js` already assumes.
- Cache integration: key on `sha256(model + ':' + text)`, read/write through an injected cache with
  `get`/`set`. Skipped entirely when no cache is supplied.
- Retry with exponential backoff on `429`/`5xx`; a permanent failure logs via `this.logger?.warn` and
  returns `null` so a single bad document cannot poison a batch.

**New · `modules/vectorStore.js`**

- One packed `Float32Array` of `capacity × dims` per container, doubling on growth, with
  `Map<docId, row>` and a free-list of vacated rows.
- `upsert(docId, vector)`, `remove(docId)`, `has(docId)`, `size`, `compact()`.
- `knn(queryVector, { k, minScore, allow })` — dot product over live rows with a bounded top-*k*
  heap, honouring an optional allow-set so hybrid can restrict to a candidate pool.
- Chunk handling: rows carry a `parentId`; `knn` max-pools chunk scores per parent so a long document
  does not flood the result list with its own fragments.
- `serialize()` → `{ buffer, meta }` and `deserialize()` for the disk layer.

**New · `modules/fusion.js`**

- `rrf(lists, { k = 60, weights })` and `weighted(lexical, semantic, { alpha })`, both taking and
  returning plain `[{ id, score }]` arrays.

**Done when:** three modules exist with unit tests, all offline. `tests/unit/searching/` shows no new
failures against the recorded baseline. Not a single line of `providers/searching.js` has changed.

### Phase 1 — Wire into the local engine  *(~2 days)*

**Edit · `providers/searching.js` — construction**

New options block, normalised by a `normalizeSemanticOptions_()` helper mirroring the existing
`normalizeSnippetOptions_()`:

```js
semantic: {
  enabled: true,
  backend: 'aiservice',     // 'aiservice' | 'hash' | custom fn
  model: 'text-embedding-3-small',
  dimensions: 384,
  mode: 'hybrid',           // default for search() when not given
  fusion: 'rrf',            // 'rrf' | 'weighted'
  alpha: 0.5,               // weighted fusion only
  k: 50,                    // per-branch candidate depth
  minScore: 0.15,
  chunk: { maxChars: 1200, overlap: 150 },
  batchSize: 64,
  maxVectorDocuments: 100000
}
```

- `createContainer_()` gains a `vectors` member — **only** when semantic is enabled, so the off path
  allocates nothing.
- **Text retention.** The engine currently keeps raw text on `doc.text` only when `snippet` is on.
  Semantic needs it to re-embed and to chunk, so enabling `semantic` must force the same retention.
  This is a real memory increase and belongs in the docs.

**Edit · `providers/searching.js` — write path**

- `indexDocumentFields_()` and `indexDocument()` call `enqueueEmbed_(id, text, containerName)` after
  the lexical index is updated.
- `enqueueEmbed_` pushes to a per-container pending list; a debounced drain embeds in batches of
  `batchSize` and upserts into the vector store.
- `flushEmbeddings(containerName)` awaits a full drain.
- `removeDocument()`, `clearIndex()`, `deleteIndex()` drop the matching vectors and any chunk
  children.
- Emit `search:embed:complete` and `search:embed:error` alongside the existing `search:add`.

**Edit · `providers/searching.js` — read path**

- `search()` reads `opts.mode` (`'keyword'` | `'semantic'` | `'hybrid'`). Absent semantic config, it
  is forced to `'keyword'` — the current code path, untouched.
- Extract today's scoring loop into `lexicalSearch_()` so the three modes compose cleanly rather than
  branching inside one long method.
- New `semanticSearch_(query, opts)`: embed the query (cache-first), `knn`, map rows back to
  documents.
- Fuse, then apply the *existing* phrase gate, `filter`, result shaping and `maxResults` slice so
  semantic hits get identical treatment. Result objects gain `vectorScore` and
  `matchedBy: 'lexical' | 'semantic' | 'both'`.
- `analytics.trackSearch` and the `search:search` event carry `mode`.

**Edit · `providers/searching.js` — persistence**

- Bump `DISK_FORMAT_VERSION` to `'3.0.0'`. Existing on-disk indexes will be treated as stale and
  rebuilt — which the loader already handles gracefully, but which must be called out in the
  changelog.
- Write `vectors.bin` (raw `Float32Array` buffer) and `vectors.meta.json` (dims, model, docId→row,
  parent map) next to the existing three files. Keep vectors out of `documents.json`: JSON-encoding
  floats roughly triples the size and the parse cost.
- On load, discard the vector store if `meta.model` or `meta.dimensions` disagree with the current
  config — vectors from a different model are not comparable, and silently mixing them produces
  quietly wrong rankings.
- `getStats()` / `getIndexStats()` report `vectorCount`, `pendingEmbeddings`, `embeddingModel`,
  `dimensions`.

**Done when:** with a stub embedder that maps known words to known vectors, a hybrid search returns a
document the keyword branch cannot find, and a keyword-only search returns exactly what it does on
`main`.

## 6. What the API looks like when it is done

The two engines are separate providers, selected by `type`. Nothing about the token engine changes.

```js
// The keyword engine — unchanged, exactly as before
const keyword = registry.searching('memory', { fields: ['title', 'body'] });

// The semantic engine — offline, zero configuration, no API key
const vector = registry.searching('vector', { fields: ['title', 'body'] });

// The semantic engine in production: embeddings via the AI service, hybrid default
const vector = registry.searching('vector', {
  fields: ['title', 'body'],
  storeFields: ['title', 'url'],
  mode: 'hybrid',
  embedding: {
    backend: 'aiservice',
    model: 'text-embedding-3-small',
    dimensions: 384
  },
  dependencies: { logging, caching, aiservice }
});

await vector.addAll(documents);
await vector.flushEmbeddings();        // only when you need determinism

await vector.search('reset my password');                      // instance default mode
await vector.search('reset my password', { mode: 'semantic', k: 20, minScore: 0.2 });
await vector.search('reset my password', { mode: 'hybrid', fusion: 'weighted', alpha: 0.3 });
await vector.search('reset my password', { mode: 'keyword' }); // its own BM25 index

// Quoted phrases hard-filter whichever branch found the document
await vector.search('Oracle "MySQL Enterprise"', { mode: 'hybrid' });

// More-like-this falls out of the vector store for free
await vector.similar('doc-1', { k: 5 });
```

The provider implements the same surface as the token engine — `add`, `addAll`, `replace`, `remove`,
`removeAll`, `search`, `indexDocument`, `removeDocument`, `loadFromDisk`, `saveToDisk`, `getStats`,
`listIndexes`, `suggest`, `autoSuggest`, `getSettings` — so the existing routes, views and
`indexerCompat` contract work against it with no changes.

## 7. Result shape

The result object gains fields; nothing is removed or renamed, so the client library, the dashboard
and `indexerCompat`'s spread-`obj` normalisation all keep working.

| Field | Status | Meaning |
|---|---|---|
| `score` | Same key | Final ranking score. In hybrid mode this is the fused score, not a BM25 score — worth documenting, since anything comparing scores across modes will otherwise be surprised. |
| `lexicalScore` | **New** | The BM25 contribution, or `null` if the document came only from the vector branch. |
| `vectorScore` | **New** | Cosine similarity, or `null`. |
| `matchedBy` | **New** | `'lexical'` \| `'semantic'` \| `'both'`. Drives the result badge in the dashboard. |
| `match`, `terms` | Unchanged | Empty for a purely semantic hit — there are no matched tokens to report. |
| `snippet` | Unchanged | Still built from matched terms. A semantic-only hit has none, so fall back to the leading text of the best-scoring chunk. |

## 8. Testing

> **Two environment facts shape this.**
> The Jest suite is **not green on a clean checkout** — record the baseline before starting and diff
> against it rather than against zero. And outbound HTTPS from Node fails with
> `SELF_SIGNED_CERT_IN_CHAIN` behind the TLS-inspecting proxy on this machine, so **no test may make
> a real embedding call**. Both point the same way: the offline path is not a nicety, it is the only
> reliable test path.

- `tests/unit/searching/embeddings.test.js` — hash determinism, normalisation, chunk boundaries and
  overlap, batching, cache hit/miss, retry and graceful failure.
- `tests/unit/searching/vectorStore.test.js` — upsert/remove/reuse of freed rows, top-*k* correctness
  against a naive reference implementation, chunk max-pooling, round-trip serialisation.
- `tests/unit/searching/fusion.test.js` — RRF and weighted fusion over hand-written rank lists,
  including the degenerate one-empty-list case.
- `tests/unit/searching/searchSemantic.test.js` — the engine with a **stub embedder** mapping fixed
  words to fixed vectors, so "semantically similar" is a property of the fixture and assertions are
  exact. Covers all three modes, the phrase gate over semantic hits, `filter` and `maxResults`
  interaction, and vector cleanup on remove/clear/delete.
- `tests/unit/searching/searchSemanticPersistence.test.js` — save/load round trip, and the
  model-mismatch discard path.
- **Regression:** `search.test.js`, `searchPhrases.test.js` and `searchTokens.test.js` must pass
  unchanged with semantic absent. Run them first, at the end of every phase.
- `tests/app/searching/app-searching-semantic.js` — a runnable demo app in the established style,
  using the hash backend so it works with no configuration.

## 9. Risks and how each is handled

| Risk | Handling |
|---|---|
| **Disk format bump invalidates existing indexes.** Every persisted index rebuilds on first load after upgrade. | The loader already treats a version mismatch as "rebuild", so it is safe — but it is a real operational cost for large indexes. Announce it, and consider a one-off migration that lifts the `2.1.0` lexical data forward and leaves vectors empty until re-embedded. |
| **Memory growth.** Vectors plus forced raw-text retention can multiply a container's footprint several times over. | 384-dim default, the sizing table above published in the docs, `maxVectorDocuments` with a warning log, and vector counts on the dashboard. |
| **Embedding cost and rate limits.** A large `addAll` is a large bill and a burst of API calls. | Batched queue, cache keyed by content hash so re-indexing an unchanged document is free, backoff on `429`, and cost visible through the AI service's existing token tracking. |
| **Silent quality regression** if a model or dimension count changes and old vectors stay in the store. | Model and dimensions are recorded in `vectors.meta.json` and the store is discarded on mismatch. Never mix. |
| **Eventual consistency surprises.** A document is keyword-searchable before it is semantically searchable. | Documented; `pendingEmbeddings` exposed in stats and on the dashboard; `flushEmbeddings()` available wherever it matters. |
| **Scope creep into a vector database.** ANN indexes, quantisation and sharding are each a project. | Explicitly out of scope. Brute force to ~100k documents, then BM25-candidate reranking. If a container genuinely needs more, the answer is a real vector store behind the `api` provider, not a hand-rolled HNSW here. |

### Sizing

Roughly **five to six focused days** for Phases 0–4, which is the complete feature including UI.
Phase 5 adds about a day and can trail. Phases 0 and 1 alone — about three days — already deliver
working hybrid search with the offline embedder, which is the point at which it is worth putting in
front of someone.

---

## 10. Deliberately not in scope

- **ANN indexing (HNSW/IVF).** Unjustified at this corpus size and a large maintenance surface.
- **A local transformer model** via `transformers.js` or `onnxruntime-node`. Genuinely attractive —
  free, private, good quality — but it adds a heavy native dependency and a model download to a
  framework that currently installs clean. Revisit once the interface has proven itself.
- **Cross-encoder reranking.** The natural next quality step after hybrid retrieval, and cheap to add
  later since `fusion.js` already owns the final ordering.
- **Semantic `autoSuggest`.** Suggestions are a token-prefix problem; embeddings do not help and
  would slow it down.
- **RAG / answer generation.** This plan delivers retrieval. Generation on top belongs in the AI
  service, consuming this one.

**Departures from the plan, all additive:**

- `knn()` uses a parent-keyed map plus a sort rather than a bounded top-*k* heap. Max-pooling by
  parent needs the map regardless, and a heap on top of it saves nothing — the sort is over distinct
  documents, not rows.
- **Added `VectorStore.removeDocument(parentId)`**, which drops a document and every chunk it owns in
  one call. Rows carry their parent, so the children are simply known. This makes Phase 1's chunk
  cleanup trivial and is strictly better than the sequential `#chunk-N` probing `indexerCompat.js`
  has to do against an external store.
- **`deserialize()` handles unaligned buffers.** A `Buffer` read back from disk is a view into Node's
  shared pool and can start at any byte offset; `Float32Array` requires 4-byte alignment. Without the
  copy-on-misalignment path, loading a persisted index would have failed intermittently and silently
  looked like "no vectors on disk". Covered by a test that deliberately misaligns the buffer.
- **`fuse()` added** as the engine-facing entry point over `rrf`/`weighted`, returning
  `{ id, score, lexicalScore, semanticScore, matchedBy }` — exactly the result fields Phase 1 needs.

**Known limitation, by design:** the `hash` backend matches shared vocabulary, not meaning. A query
for "reset my password" finds a document titled "Credential recovery procedure" only if that document
also literally contains those words. It exists for deterministic tests and a zero-configuration dev
path; real semantic matching arrives with the embedding models in Phase 2.

**Bug found and fixed during testing:** the default `minScore` of `0`, combined with `knn`'s
`score < minScore` comparison, returned documents with *zero* cosine similarity — orthogonal to the
query, and never a legitimate result. Every semantic search ended in a tail of unrelated documents,
and in hybrid mode those documents were mislabelled `matchedBy: 'both'`. The default is now `1e-6`,
which says only "must be positively similar"; a real relevance bar is still the caller's to set.

**Not carried over from `searching.js`, deliberately:** prefix and fuzzy query expansion, and the
synonym map. Prefix and fuzzy matching are compensating for vocabulary mismatch, which is the exact
problem embeddings solve directly — and synonyms are a hand-maintained approximation of what the
vector branch does automatically. Callers who want them have the `default` provider.
